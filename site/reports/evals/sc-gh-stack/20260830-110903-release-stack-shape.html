That approach could work, but it's not the ideal shape. The issue is that **gh stack is designed for parallel feature branches, not sequential integration**.

Here's the problem with two layers:
- Layer 1 (`release/0.6.0 → develop`): Has version bump + changelog
- Layer 2 (stacked on Layer 1, `→ main`): Would contain the *same* version bump + changelog commits *plus* a merge of Layer 1

When `gh stack merge` runs, it will merge both sequentially, but Layer 2 ends up "re-merging" code that Layer 1 already integrated into `develop`. This works, but it's redundant and makes your `main` history less clean.

**Better approach: Sequential PRs (simpler)**
1. Merge `release/0.6.0 → develop` (wait for CI)
2. Then open `develop → main` as a separate PR and merge

This is explicit, clear, and avoids the merge redundancy. You don't need `gh stack` for a linear release flow—it's overkill.

**If you want to automate the sequential land:** Use `gh pr merge` with `--auto` on the first PR, then immediately open and merge the second. Or script it. But don't force it through gh stack.

**Exception:** *Only* use the two-layer stack if you're trying to keep both PRs open simultaneously while their CI runs in parallel before you land them. In that case, make sure your second layer targets `main` *after* syncing to `develop`'s latest, not stacking commits on top.

Recommendation: Skip gh stack here. Sequential PRs are clearer and more maintainable.

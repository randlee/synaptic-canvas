final message
No. That stack is unsafe:

```text
(develop) <- release/0.6.0 <- develop -> main
```

The lower PR would mutate `develop`, which is the protected head of the upper PR. That invalidates the upper PR’s gated CI and cannot be safely rebased during the cascade.

Because you require this exact order, use two sequential, independent merges:

1. Merge `release/0.6.0 -> develop` as a standalone PR. Wait for required CI and approval.
2. After it lands, update/open `develop -> main`, wait for fresh required CI and approval, then merge it.

Do not link those PRs into one stack or run `gh stack merge --yes` on that shape.

If you prioritize one stack merge over the exact intermediate landing order, the supported carry-layer shape is:

```text
(main) <- develop <- release/0.6.0
```

That makes `develop -> main` the bottom layer and `release/0.6.0 -> develop` the top layer. The stack merge lands `develop` into `main`, then retargets the release layer to `main`; a final `main -> develop` merge-forward is then required. This is only appropriate if your branch-protection rules and merge queue do not force fresh base updates mid-cascade.

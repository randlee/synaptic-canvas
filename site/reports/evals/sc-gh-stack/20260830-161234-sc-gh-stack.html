final message
That shape has a problem: **gh stack is built for commits that chain within a single base branch, not for sequential operations across different targets.**

Here's the issue: when you merge layer 1 (`release/0.6.0 → develop`), the `develop` branch moves forward. But layer 2's branch was based on the *old* `develop` state before the merge. After layer 1 lands, layer 2 is potentially stale and `gh stack merge` may not handle the rebase correctly—or may conflict.

**What you should do instead:**

1. **Just merge them sequentially** (simplest and clearest):
   ```bash
   # Create and land PR1
   gh pr create --base develop --title "Release 0.6.0"
   gh pr merge <PR1> --squash  # (or your preferred merge strategy)
   
   # Create and land PR2
   gh pr create --base main --title "Release 0.6.0 to main"
   gh pr merge <PR2> --squash
   ```

2. **Or if you want automation**: Create both PRs first, then:
   ```bash
   gh pr merge <PR1> && gh pr merge <PR2>
   ```
   This waits for CI on each before merging—both branches are protected so it will enforce that anyway.

**If you really want gh stack**, you'd need to create a temporary tracking branch, which defeats the point. The mental model doesn't fit.

What's your reason for preferring the stack approach—is it about history, preventing manual steps, or something else? That might suggest a better workflow.

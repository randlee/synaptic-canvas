final message
Your plan has a problem: `gh stack merge` isn't the right tool for this flow.

A gh stack merges a chain of commits stacked on one base branch—each PR depends on the one below it. When you merge with `--yes`, it does all of them in sequence. But your scenario is different: you need two sequential **PRs to different targets**, where the second PR's source branch needs to be updated after the first PR lands in `develop`.

**What happens with your approach:** When PR1 merges into `develop`, the `develop` branch updates. PR2 was created pointing to the old state of `develop`, so you'll get a merge conflict or stale state.

**Better options:**

1. **Sequential merges (simplest):** Create both PRs, merge the first one, wait for CI on `develop`, then merge the second one. This is straightforward and requires no stack gymnastics.

2. **CI-gated sequential merge:** Set up the second PR to require the first one to be merged before it can merge (via branch protection rules or just manual sequencing), then merge both in order.

The gh stack is built for stacking independent feature commits on a single base branch, not for progressive merge-ups across multiple branches. Save it for cases where you have multiple independent PRs all landing into `main` and you want to land them together.

For a release flow, sequential merges are clearer and safer.
